# PRD 3.2 性能根因剖分与技术路线决策（2026-11-11）

## 0. 证据范围和结论等级

**已实测**：DEV60 中 60 张图片、171 个 V5 预测实例，原始 Stage2 8 个批次、513 次正式 Qwen 调用（Tags/VQA/Copy 各 171 次）；RTX 4090 24 GiB；BF16（GPU 支持时）/FP16，SDPA、Qwen2.5-VL-7B-Instruct、V5 和 Qwen 常驻同一进程；模型及 Prompt 不变，独立 Holdout 未使用，Guard 无自动放行。

**本次新增**：直接复算原始 qwen_calls.jsonl 的真实输出 token、生成/预处理/任务耗时，按任务拟合生成耗时与输出 token 的关系，检查实际输出规范；与 PRD V1.1 指标逐项对齐。

**估算**：RTX 4090 显存带宽约 1008 GB/s；按约 7.6B 的语言解码权重、每参数 2 byte 估算纯读取下界约 15.1ms/token，对应理想带宽上限约 66 tokens/s。该估算不含视觉预填充、KV cache 访存、kernel launch、同步、分词、调度等；不代表实测速度，也不代表任何推理后端一定达到 66 tok/s。

**未测**：纯 decode CUDA kernel 时延、首 token TTFT、预填充时间单独计量、有效 KV cache 实际状态、SM/显存带宽实时利用率、改变输出格式或量化后的真实性能/质量。这些需要 GPU 专用探针或新 A/B 才能宣称。

## 1. 现行调用结构

执行路径：V5 推断→每个目标画红框→重复 3 次将同一带框完整图送入 Qwen2.5-VL-7B→独立生成 Tags、颜色 VQA、Copy→Guard。V5 Mask 仅用于一致性校验，不作为 Qwen 像素输入。3.1.2/3.1.3 没有因此等同于完整接入。Qwen 加载约 5.08s（不计入暖态请求）；V5 和 Qwen 同进程，模型加载后仍有约 7.54GiB GPU 空余。Qwen 模型以 `attn_implementation='sdpa'`、`max_pixels=512*28*28` 初始化；原真实 decode helper 内使用 `torch.inference_mode()`、`do_sample=False`、按任务限制 max_new_tokens。模型 config 写有 `use_cache=true`，但此前并未动态验证缓存实际工作状态。

## 2. 原始端到端时延

| 模块 | 均值 ms | 百分比（总 2362.77ms） |
|---|---:|---:|
| V5 | 50.09 | 2.12% |
| Qwen Tags | 1253.78 | 53.06% |
| Qwen VQA | 243.13 | 10.29% |
| Qwen Copy | 811.66 | 34.35% |
| Guard | 0.15 | 0.006% |
| 其他封装/差值 | 3.96 | 0.17% |

平均端到端 2362.77ms，P95=2759.17ms，最大=3095.23ms。Tags+Copy =2065.44ms，占端到端 87.4%；三个 Qwen 任务合计 2308.57ms，占约 97.7%。这里的“任务耗时”包括图像/文本预处理和 generate()，不等同于纯 decode。

## 3. 真正的 token / prefill / decode 成本

| 任务 | n | Token均值 / 最大 | cap | 预处理均值ms | generate()均值ms | 任务总均值ms | `generate_ms ~ 截距 + 斜率×tokens` |
|---|---:|---:|---:|---:|---:|---:|---|
| Tags | 171 | 41.91 / 51 | 170 | 30.02 | 1219.38 | 1253.78 | 158.20 + 25.32×token |
| VQA | 171 | 3.30 / 15 | 128 | 29.23 | 211.06 | 243.13 | 127.27 + 25.41×token |
| Copy | 171 | 25.53 / 44 | 120 | 29.11 | 779.61 | 811.66 | 143.56 + 24.91×token |

- **171 个实例累计生成 12097 Token，平均 70.74 Token/实例**。三任务合计约 88.36ms CPU/GPU 预处理（3 次×约 29.5ms），但三次 `generate()` 均值合计约 2210.06ms；三次视觉/文本 prefill 隐含在后者中。
- 回归斜率 24.9–25.4ms/Token，对应约 39–40 Token/s 的**经验边际速率**；不是“纯 decode kernel 测速”，因为样本图像、输入长度/任务内容不同，且没有单独 TTFT 埋点。
- 各任务 token 分布明显低于当前 cap（170/128/120）。**单调减小 cap 而实际输出不变，不会显著减少耗时**；过度限制会截断 JSON 或破坏语义。
- VQA 的简单短答只有 2 token 的样本很多，仍需首轮视觉 prefill 和模型启动，因此以 `3.30/211ms` 直接换算真实解码 tok/s（得 15.6）会**误导**；这些短答的常数项占比很高。
- 现有 `model_runner_timing.generation_ms` 从 `model.generate` 前后取点，**包含整段 prefill 和逐 token decode**；`batch_decode` 在该字段之后，不是完整服务时延。

## 4. 理论带宽 Roofline（不是 GPU 实测）

NVIDIA RTX 4090 24GB 的官方峰值显存带宽为 1008GB/s。Qwen2.5-VL-7B 使用与约 7.6B 级语言模型相当的解码主干；以 BF16 2B/参数估算，解码时权重扫描流量约 15.2GB/token。若完全由理想带宽决定，约 15.1ms/token（66 tok/s）。

- 当前经验边际 25.2ms/token、约 39.7tok/s，约为上述理想速率的 60%。这不是“GPU 只用到 60%”的测量，额外开销包含 KV/cache、kernel、计算、调度及输入差异。
- 仅对当前平均 70.74 个输出 Token，**BF16 理想权重访问下界就约 1.07 秒**，尚未加三次视觉 prefill、V5、预处理等开销。这不是全流程数学严格下界（具体缓存与并行方案可变化），而是对当前批量=1、三次独立生成架构的粗略 Roofline。
- 因而在不改变模型精度、输出 token 总量及串行结构时，仅靠低层常数优化达到完整 400ms **缺乏可行性**。Copy 平均 25.53 Token，仅 BF16 权重带宽近似下界也约 386ms，在这个架构下**不可能稳妥满足100ms完整单商品生成**。
- INT8/INT4 量化能降低权重访存的理想下界，但真实速度取决于反量化内核、GPU、视觉前端、KV cache、批处理及输出质量。不能按“INT4=必然4倍速”推算验收通过，更不能只量化不做质量回归。

## 5. 输出规范与 PRD 逐项核对

1. **结构化属性 Tags**：171/171 原始输出可以从 Markdown 代码围栏中提取合法 JSON，且字段**固定只有** `category,primary_color,pattern,visible_design` 四项。**171/171 原样输出包含 ` ```json ` 代码围栏，并非可直接交付的纯 JSON**；需剥离围栏并校验 schema。PRD3.2.2 要求商品细粒度属性标签（JSON格式）、准确率≥90%。当前 4 字段覆盖有限，尚未证明满足正式细粒度字段集；不过带教已豁免面料/工艺等复杂属性，最终必须按实际确认的缩减字段集验收，不能机械套原 14 大类。
2. **VQA**：本轮问答主要是固定的颜色问题，171 条平均原始响应仅 4.06 字符，不能证明已覆盖原 PRD 的属性查询、设计解析、工艺说明与穿搭建议四类问题。VQA 任务均值 243.13ms，对比原要求“回答生成≤200ms”超出 21.6%；只计内部 `generation_ms` 均值 211.06ms，超出约 5.5%。完整任务≤200ms为 34/171；内部 generate()≤200ms为 136/171，两者不能混用。
3. **Copy**：本轮输入硬编码 `length_chars=[20,80]`，实际输出 20–56 个字符、均值 32.53，171/171落在本轮固定长度窗口，但这**不等于验证了 PRD 所需的风格与长度可自定义**。89/171 文案出现“红框/图中/框内”等图像标注或非商家文案用语，需要清理；更重要的是有无依据内容和对象串扰需要人工评估。
4. **单商品生成时间≤100ms**：若仅指 Copy，当前 811.66ms，约目标 8.12 倍；若指 Tags+Copy，则约 2065.44ms，约目标 20.65 倍。计时起止口径必须与带教明确，不能自行把多个目标混写。
5. **系统交互平均≤400ms / 60QPS RTX3090**：当前独立目标请求三任务串行均值 2362.77ms，约 5.91 倍目标，但单实例三任务的“请求”与原 PRD 单轮多模态交互的测试范围可能不完全同义，且当前运行在 RTX4090 而不是 RTX3090；不可直接声明最终系统已不达标或“不可能满足60QPS”，必须先统一接口定义和并发条件。
6. **Guard**：171/171 阻断，0 条自动放行。这保护了风险，但“发布正确内容的覆盖率”为0，目前不能以只看获放行样本的条件准确率作为质量成果。

## 6. 技术路线判断

**当前决策：先明确输出契约和真实 decode 能力，优先测试改变调用结构，量化是次要受控候选；不建议先直接把 170/128/120 的 cap 降低。**

优先测试顺序（每次仅改一项，并保持同组 DEV60 样本）

1. **GPU decode-only 仪表化测试**：附 `gpu_decode_probe.py`，针对原始冻结 Qwen 输入，记录首 token 与后续逐 token 的实际完成间隔，并和 uninstrumented Stage2 参照比对。输出必须与 Baseline 相同，否则不计为有效等价加速方案。
2. **规范输出契约**：按导师批准字段列表定义紧凑 JSON schema；去 Markdown 围栏、去无效装饰性文本，明确 VQA 的四类问题与 Copy 风格/长度。**先定义正确内容，再谈减少 token**。
3. **任务分路/复用方案**：尝试 Tags 与 Copy 共享视觉处理结果或合并调用后再解析，也可基于结构化属性以受约束模板生成商家文案；VQA按需调用而非每个目标无条件三连。不要把多任务合并损失/串扰的质量风险忽略。
4. **选择性模型替换与量化**：保持7B FP16/BF16 基线，对小模型、INT8/INT4 候选进行冻结样本 A/B。优先看 p50/p95、显存、质量、Guard放行覆盖，不能只看平均延迟。
5. **最终专项验收**：定义在线延迟终点（TTFT、完整回答、是否含属性/文案生成）、单商品和多商品请求区别、RTX3090/4090测试口径，再在独立 Holdout 中冻结候选评估。

## 7. 当前仍缺的关键实测证据

原始日志没有 **逐 Token 时序、视觉 token 数、输入 token 数、首 Token 完成时刻、实际内存带宽/利用率、KV cache 是否有效复用**。附带 GPU 探针可以增加首 token 和 decode token 间隔记录，但它通过 streamer 每步同步，有观测扰动，因此须将结果视为“仪表化近似”，不能宣称 CUDA kernel 理论峰值。

## 8. 一句话交付结论

> 当前 Qwen7B 的真实慢点是三次串行多模态生成，平均输出约71 Token，边际生成成本约25ms/Token；Tags与Copy贡献87.4%端到端耗时。原始输出在 JSON纯净性、多类型VQA与文案定制方面尚未完整覆盖 PRD。按4090带宽粗略估算，当前BF16解码量仅理想权重流量就约1.07秒，因此达标方案不能只靠调低 token cap；应先做逐 Token 实测和输出契约验证，再优先评估任务路由/模板化/模型替换，量化作为受控对照。
